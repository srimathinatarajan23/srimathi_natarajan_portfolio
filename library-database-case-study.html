Library Book Borrowing System & Database Architecture

Designing, modeling, and populating an enterprise relational database system — a database engineering case study.

As part of OPIM 5272 (Database Management) at the University of Connecticut School of Business, Team 1 designed and implemented an end-to-end Physical Entity Relationship Model and Data Population strategy for a multi-branch Library Book Borrowing System.

Modern library operations demand strict data integrity across member accounts, book copies, active loans, reservations, fines, and branch inventories. Our objective was to construct a robust 3NF relational database architecture with complete constraint enforcement and verified statistical data populations.

Enterprise Library Database Architecture

Database Design & Data Engineering

2026 · UConn School of Business (OPIM 5272)

WHAT WE DID

Architected a complete relational database for library branch operations. Modeled member inheritance (Adult vs. Child subtypes with total specialization and disjoint constraint), loan tracking, reservation queues, fine assessment, author bibliographies, and book copy availability across branches.

HOW WE DID IT

Developed logical and physical Entity Relationship Diagrams in DBeaver. Enforced primary key/foreign key constraints, non-null requirements, and unique indexing. Populated every table with valid data records adhering to strict relational constraints.

RESULTS

Delivered a fully verified database instance with 50+ records populated per entity table. Generated statistical summary reports confirming zero orphan records, accurate row counts, and optimized table storage metrics.

TOOLS & TECHNOLOGIES

SQL MySQL / InnoDB DBeaver Physical ERD Data Modeling Relational Integrity

How We Approached It

From conceptual requirement modeling to physical SQL table population and statistical verification.

STEP 01 · ENTITY ARCHITECTURE & SUBTYPES

Member Inheritance & Constraints

We structured member accounts into a supertype-subtype relationship:

  • Supertype: MEMBER (holds contact info, email, join date, branch ID)
  • Subtypes: ADULT (Government ID, Payment Type) and CHILD (Guardian Name, Max Books Allowed)
  • Constraints: Enforced total specialization (every member MUST be an Adult or Child) and disjoint constraint (a member cannot be both).

STEP 02 · PHYSICAL ERD DESIGN

Normalizing Relationships in DBeaver

Modeled 1:N and M:N relationships across operational domains:

  • LIBRARY_BRANCH → STAFF & BOOK_COPY
  • BOOK → AUTHOR, GENRE, SUB_GENRE
  • LOAN & RESERVATION → BOOK_COPY & MEMBER
  • FINE → LOAN & MEMBER

STEP 03 · DDL CREATION & CONSTRAINT ENFORCEMENT

Strict Schema Rules

Wrote DDL scripts in SQL defining precise data types (e.g. DECIMAL(6,2) for fines, VARCHAR(100) for emails, DATETIME for loan tracking) and foreign key CASCADE/RESTRICT rules to prevent invalid deletions.

STEP 04 · SQL DATA POPULATION

Generating Realistic Test Populations

Populated 50+ valid records into each table. Ensured foreign key references existed before child row inserts, maintaining 100% referential integrity across all 12 tables.

STEP 05 · STATISTICAL AUDITING & DBERVER VERIFICATION

Table Statistical Summaries

Ran table statistics tools in DBeaver (InnoDB engine) to inspect row counts, data lengths (16K pages), index lengths, and update timestamps across all entities.

STEP 06 · OPERATIONAL VALIDATION

Query Testing

Verified critical business queries: identifying overdue loans, calculating outstanding member fines, looking up book copy availability per branch, and auditing active reservations.
